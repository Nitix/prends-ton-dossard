# Prends ton dossard v9 — a registration opening per race — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A format (« épreuve ») can have its own registration opening — day and time, day alone or time alone, the missing part taken from the event's — and everyone sees, is reminded of and has in their calendar the opening of their own format; without one, the event's (« l'ouverture générale »).

**Architecture:** Two new text fields on `formats` (migration `9s`). One pure rule says which opening holds for whom (§ 4.2 of the spec), written once in TypeScript (`web/src/features/events/opening.ts`) and once in Go (`server/events/openings.go`); every consumer (hero, card, home, share, `.ics`, reminders, feed, MCP) asks it instead of reading `events.registration_opening`. The hooks of `server/events` hold the new rules; the form and the MCP send the fields in an order the hooks accept.

**Tech Stack:** Go 1.27 + PocketBase v0.41 (`server/`), React 19 + TanStack Query + Vitest 5 browser mode (`web/`).

**Spec:** `docs/superpowers/specs/2026-11-14-courses-v9-design.md` (read it whole before any task; § numbers below refer to it). It builds on the v7 spec (`2026-11-07-courses-v7-design.md`, § 3 and § 4).

## Rulings (from planning)

- Ruling: an `Opening` carries `formatIds` (empty = the event's own); openings of one person with the same instant are merged into one, the event's winning, else the union of format ids sorted. — One rule for "one reminder per instant", the names in parentheses and the calendar. — If wrong: a person sees one line for two formats that open together, which the spec allows.
- Ruling: the spec's form order (§ 4.3, « effacée ou avancée … retardée ») is implemented with the existing "waits" pattern of `buildBatch`: a format's opening that the **stored** event would refuse (day after the stored deadline or first day, or a partial value while the stored event has no opening) is sent empty in phase 2 and set in phase 4, after the event. — Same guarantee (no refused intermediate state), fits the four existing phases, ports to `planBatch` the same way. — If wrong: one failing batch shows the error under the format's field; nothing is half-saved (batches are transactions).
- Ruling: the calendar UID of a merged format opening uses the smallest format id. — Stable while that format keeps its opening. — If wrong: an entry is replaced once in a subscribed calendar.
- Ruling: in a merge, a partial format opening is completed from the merged event; if it then has no time while the kept event has none of its own or has a time, it is cleared and counted (otherwise it would take another event's time). — Rare case; never a silent change of meaning. — If wrong: one opening to type again, which the merge preview says.
- Ruling: the MCP `home` needs the formats of each event (for the opening of an undecided participation): its query expands `event.formats_via_event`. — The derived general opening needs them. — If wrong: a heavier query on the home tool only.
