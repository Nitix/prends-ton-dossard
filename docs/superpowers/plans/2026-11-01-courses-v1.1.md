# Courses entre amis v1.1 : plan d'implémentation

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Objectif :** corriger ce que le groupe a remonté après la v1 :
- s'inscrire à plusieurs épreuves d'un même événement ;
- masquer les « Non partant » ;
- se dire intéressé par un événement avant d'avoir choisi l'épreuve ;
- compiler les composants avec le React Compiler natif, sans Babel ;
- afficher une photo de profil à la place des initiales.

**Architecture :** inchangée. Un programme Go utilise PocketBase comme bibliothèque et sert une SPA React. Le serveur porte les règles :
- une migration ajoute `participations.event` et `runners.avatar` ;
- des hooks de modèle gardent l'invariant « une participation à l'événement ou des participations à des épreuves, jamais les deux », et font la conversion ;
- la fusion d'événements est adaptée.

Le front lit toutes les participations d'un événement par la relation inverse `participations_via_event`, puis les range par épreuve.

**Stack :**
- **Serveur** : Go, PocketBase v0.41.1 (module `ganigeorgiev.com/pocketbase/pocketbase`).
- **Front** : TypeScript, React 19, `@vitejs/plugin-react` 6.1.2 avec `react({ compiler: true })` et `oxc-transform-react` 0.152.x (Task 6), Vite 8 (Rolldown), Tailwind 4, TanStack Router et Query, SDK JS de PocketBase, Temporal, Intl.
- **Outils** : oxlint, oxfmt, Vitest (node et browser mode), pnpm, Node ≥ 26.

**Spec :**
- `docs/superpowers/specs/2026-10-31-courses-design.md` : la v1 ;
- `docs/superpowers/specs/2026-11-01-courses-v1.1-design.md` : l'addendum v1.1, qui l'emporte en cas de conflit.

Lis l'addendum avant chaque tâche : le plan renvoie à ses sections (§).

## Conventions PocketBase utilisées dans les tests

Inchangées depuis la v1. Quand une règle refuse, PocketBase répond :
- **list** : `200` avec une liste vide ;
- **view, update ou delete** : `404` ;
- **create** : `400` ;
- **règle `null`** : `403`.

Une erreur de validation répond `400` avec `data.<champ>.code`. Une contrainte unique violée à l'insertion devient `validation_not_unique` sur les champs de l'index.

**Hooks** (§ 4.2 de l'addendum), tous de modèle :

### Task 2 : Fusion d'événements avec les participations sans épreuve

**Files :**
- Modify : `server/admin/merge.go`
- Test : `server/admin/merge_test.go`

**Interfaces :**
- Consumes : le schéma de la Task 1 (`participations.event`, `format` facultatif).
- Produces : `MergeResult` **inchangé**. C'est le contrat JSON avec `describeMerge` (front, v1 Task 23). `MergeEvents` et `MergeFormats` gardent leur signature.

**Comportement de `MergeEvents`** (§ 4.3 de l'addendum), dans la transaction, avec `dryRun` qui compte sans écrire :
1. **Les épreuves** passent sur l'événement gardé, avec leur date effacée si elle sort de la plage (v1).
2. **Les participations de ces épreuves** suivent : `event = keep` (`tx.Save`). Elles comptent dans `MovedParticipations`, comme en v1.
3. **Les participations sans épreuve de l'événement gardé** dont le coureur a maintenant une participation à une épreuve déplacée sont supprimées (`DroppedParticipations`).
4. **Les participations sans épreuve de l'événement fusionné** :
   - supprimées (`DroppedParticipations`) si le coureur a, dans l'événement gardé, une participation sans épreuve ou une participation à une épreuve (gardée ou déplacée) ;
   - sinon, `event = keep` (`MovedParticipations`).
5. **L'événement fusionné** est supprimé. Il n'a plus rien à supprimer en cascade.

L'ordre compte :
- l'étape 2 avant les étapes 3 et 4, car la validation exige `format.event == event` ;
- les suppressions de l'étape 4 avant les déplacements, à cause de l'index `(runner, event) WHERE format = ''`.

`MergeFormats` ne change pas.
